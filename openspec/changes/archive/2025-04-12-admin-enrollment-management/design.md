## Context

后端 AdminEnrollController 已完整实现 5 个管理端 API（列表、详情、通过、拒绝、统计），前端侧边栏已配置 `/admin/enroll` 路由，但无对应页面文件。本次变更为纯前端开发，不需要修改后端。

现有前端基础设施：
- Admin Layout（AdminHeadBar + AdminSideBar）已就绪
- 已有 `apiClient`（带 CSRF/认证）和 `publicClient` 两种 HTTP 客户端
- 已有部分报名类型定义（`EnrollmentBriefDTO`、`EnrollStatus`、`Direction`），但缺少管理端专用类型
- Ant Design 6 暗色主题，Tailwind CSS 4

## Goals / Non-Goals

**Goals:**
- 提供完整的报名管理界面，让管理员可以浏览、搜索、筛选报名数据
- 支持通过/拒绝操作，拒绝时可填写原因
- PC 和移动端统一使用卡片布局，通过 Tailwind 响应式断点适配
- 点击卡片通过 Drawer 查看详细信息

**Non-Goals:**
- 不修改后端 API
- 不实现批量审批功能
- 不实现导出功能
- 不新建独立的管理端 layout 或路由框架（复用现有 admin layout）

## Decisions

### 1. 卡片布局（统一 PC/移动端）

**选择**：统一使用 Ant Design `<Card>` 组件，PC 端 3 列网格、移动端单列。

**理由**：避免 Table 和 Card 两种布局的响应式适配问题。卡片在两种尺寸下表现一致，仅需调整网格列数。

**实现约束**：代码实现时**必须优先使用 Ant Design 的 `<Card>` 组件**作为报名卡片容器，利用其内置的边框、圆角、hover 效果和暗色主题适配能力，而非用 div 手动模拟卡片样式。统计卡片和卡片网格中的每张报名卡片均使用 `<Card>` 或 `<Card.Meta>` 组件。

**UI 设计稿**：详见 `docs/UI/admin-enroll-management.pen`，包含 PC 视图（1200px）、详情 Drawer、拒绝 Modal 和移动端视图（375px）。

### 2. 搜索机制

**选择**：单个 Input.Search，后端 `keyword` 参数同时匹配姓名和学号。

**理由**：后端已支持 `keyword` 参数做模糊搜索，前端只需一个搜索框，交互简洁。

### 3. 审批操作

**选择**：
- 通过：点击直接生效，无二次确认
- 拒绝：点击弹出 Modal，包含 textarea 填写原因（可选，最多 200 字）+ 确认按钮

**理由**：通过操作虽不可逆（创建用户），但管理员在管理界面操作属于明确意图。拒绝需要原因留痕，Modal 提供足够空间。

操作按钮出现在两个位置：
1. 卡片行内（快捷操作）
2. Drawer 详情底部（看完详情后操作）

两处操作共享同一个状态更新逻辑，操作成功后刷新列表。

### 4. API 调用策略

**选择**：页面加载时并行请求统计数据和列表数据。切换筛选/翻页时仅重新请求列表数据。

**理由**：统计数据变化频率低，但为简单起见，每次筛选变更时也刷新统计。使用 `useCallback` + `useEffect` 管理数据获取。

### 5. 文件结构

```
src/frontend/src/
├── app/admin/enroll/page.tsx          # 报名管理页面（Client Component）
├── apis/services/admin-enroll.service.ts  # 管理端报名 API Service
└── apis/schema/type.ts                # 补充管理端类型定义
```

不拆分子组件——单文件内聚，通过函数组织代码区域。如果后续页面膨胀再考虑拆分。

## Risks / Trade-offs

- **单文件可能过大** → 如果超过 500 行，考虑将 Drawer 内容和统计卡片提取为独立组件
- **统计数据与列表数据不同步** → 操作后统一刷新两个接口，保持一致性
- **移动端 Drawer 空间有限** → Ant Design Drawer 在移动端默认全宽，体验尚可
