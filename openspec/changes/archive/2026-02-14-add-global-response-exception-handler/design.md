## Context

当前项目接口返回格式缺乏统一规范，异常处理分散在各控制器或业务层，导致前端解析复杂、错误语义不一致，且难以统一记录与追踪。需要在不大规模修改业务逻辑的前提下，引入统一响应体与全局异常处理，使返回结构和错误码具有一致性。

## Goals / Non-Goals

**Goals:**
- 定义统一响应体结构并提供便捷的构建方式
- 通过全局异常处理器覆盖常见异常并映射为统一响应
- 形成明确的错误码与消息规范，便于前后端协作
- 尽量减少对现有业务代码的侵入

**Non-Goals:**
- 不在本次变更中完善所有业务异常的细粒度枚举
- 不改造与响应体无关的业务逻辑与数据模型
- 不引入新的第三方框架或改动整体架构

## Decisions

- 采用全局响应包装模型 `ApiResponse<T>` 统一格式，提供静态工厂方法（success/fail）减少重复代码。
  - 备选方案：在各 Controller 里手工构造 Map/JSON；缺点是重复劳动、容易不一致。
- 使用 `@RestControllerAdvice` + `@ExceptionHandler` 作为全局异常处理器。
  - 备选方案：在过滤器层捕获异常；缺点是难以区分业务异常、也不利于返回统一业务错误码。
- 统一错误码策略：预留区间区分系统错误、参数校验错误、业务错误；默认错误消息通过枚举集中维护。
  - 备选方案：直接使用 HTTP 状态码；缺点是无法满足业务语义扩展与国际化。
- 响应包装策略：仅对应用层 API 生效，允许对下载/文件流、第三方回调等场景做白名单豁免。
  - 备选方案：全量包裹；缺点是影响文件/流式响应。

## Risks / Trade-offs

- [兼容性风险] 统一响应体可能影响历史客户端解析 → 提供兼容期或在网关/前端做适配说明
- [异常覆盖不足] 未覆盖的异常可能返回默认错误 → 提供兜底异常处理与日志
- [性能影响] 统一包装带来少量序列化开销 → 影响可接受，且可通过白名单规避
