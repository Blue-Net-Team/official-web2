## Context

当前系统中有两个与"竞赛"相关的模块：

1. **团队成就（Achievement）**: 通过 `tb_achievement.relate_to` 字段存储关联项文本。当类型为 `COMPETITION` 时，`relate_to` 期望与 `tb_competition.name` 匹配，用于在查询时批量加载竞赛 Logo 和简称。
2. **团队竞赛库（Competition）**: 维护竞赛基本信息，包括名称、简称、Logo、封面等。

现有代码中，成就与竞赛之间没有外键，仅靠字符串精确匹配。管理员在创建/编辑成就时通过自由文本输入关联项，容易因拼写错误、大小写差异或多余空格导致匹配失败，且系统不会提示，竞赛 Logo 和简称会静默丢失。

## Goals / Non-Goals

**Goals:**
- 确保 `tb_competition.name` 全局唯一，作为成就与竞赛之间的稳定关联键。
- 在应用层校验竞赛名称唯一性，避免直接暴露数据库约束异常。
- 前端创建/编辑竞赛成就时，提供已有竞赛选项，减少手动输入错误。
- 统一对输入值进行 `trim()`，消除前后空格导致的匹配失败。
- 允许管理员输入尚未录入竞赛库的新竞赛名称，保持操作灵活性。

**Non-Goals:**
- 不修改 `tb_achievement` 表结构，不引入 `competition_id` 外键。
- 不改变论文（PAPER）和专利（PATENT）类型的"关联项"输入方式。
- 不处理历史成就数据的批量清洗或迁移。
- 不将个人竞赛经历（`tb_user_experience`）与团队成就打通。

## Decisions

### 1. 关联机制：继续采用 `relate_to` 字符串匹配，而非外键

**决定**: 保持 `tb_achievement.relate_to` 为字符串字段，通过唯一竞赛名称建立隐式关联。

**理由**:
- 改动最小，无需迁移现有成就数据。
- 允许"先录成就、后补竞赛"的工作流，新输入的竞赛名后续可被竞赛库收录并自动关联展示。
- 符合当前代码中已存在的 `AchievementRepositoryImpl.selectByNames` 批量匹配逻辑。

**替代方案**: 在 `tb_achievement` 中增加 `competition_id` 外键。被否决，因为需要数据迁移，且会强制"必须先建竞赛再录成就"，降低灵活性。

### 2. 唯一性约束：数据库约束 + 应用层校验

**决定**: 通过 Flyway 迁移为 `tb_competition.name` 添加 `UNIQUE` 约束，并在 `CompetitionAppServiceImpl` 中增加显式唯一性校验。

**理由**:
- 数据库约束是最终防线，防止并发或绕过服务层直接写库导致重复。
- 应用层校验提供更友好的错误信息（如"竞赛名称已存在"），避免将数据库异常直接抛给前端。

### 3. 前端输入控件：条件渲染 Select/Input

**决定**: 在 `AchievementDrawer.tsx` 中，根据成就类型动态切换 `relateTo` 字段的输入控件：
- `COMPETITION`: 使用 antd `Select`（`showSearch` + `allowClear`），选项来自现有竞赛列表，允许输入不存在的名称。
- `PAPER` / `PATENT`: 保持原有 `Input` 不变。

**理由**:
- 直接解决手动输入竞赛名称时的拼写错误问题。
- 允许输入新竞赛名称，保持流程灵活性。
- 论文/专利没有对应实体库，无需改动。

### 4. 输入规范化：前端保存前 trim

**决定**: 前端在提交表单前对 `relateTo` 执行 `trim()`；后端在领域实体 `Competition.create()` / `update()` 中已有的 `name.trim()` 保持不变；`Achievement` 查询匹配时不额外 trim（因为 `relate_to` 已是规范化后的值）。

**理由**:
- 消除 `"蓝桥杯 "` 与 `"蓝桥杯"` 这类不可见差异导致的匹配失败。
- 避免在查询层做隐式 trim，保持数据库存储与查询逻辑的一致性。

### 5. 竞赛列表数据源：复用现有公开接口

**决定**: 前端调用 `GET /api/v1/competitions?limit=1000` 获取竞赛名称选项。

**理由**:
- 现有接口已支持 `limit` 参数（最大 50）。如果竞赛数量可能超过 50，可后端临时调大 limit 上限，或新增 `/api/v1/competitions/names` 轻量接口。本次先复用现有接口，若数据量增长后再优化。

## Risks / Trade-offs

- **现有竞赛名称重复** → 部署前需检查 `tb_competition` 是否存在重复 `name`。若存在，需先人工清洗数据，否则迁移失败。
- **并发创建同名竞赛** → 数据库唯一约束会兜底，应用层校验负责返回友好错误，两者结合可覆盖并发场景。
- **输入不存在的竞赛名称** → 成就卡片会 fallback 到标题 + 默认图标。这是设计上的有意行为，但管理员需要知晓：新竞赛名后续被录入竞赛库后，旧成就会自动展示 Logo。
- **大小写差异** → 当前匹配是大小写敏感的。`trim()` 解决空格问题，但大小写差异仍需管理员注意。Select 组件选择已有选项时可完全避免此问题。

## Migration Plan

1. 检查线上 `tb_competition` 表是否存在重复 `name`；如有重复，先人工合并/清洗。
2. 部署包含 Flyway 迁移的后端版本，为 `tb_competition.name` 添加 `UNIQUE` 约束。
3. 部署后端应用层校验和前端改动。
4. 回滚策略：如出现问题，可回滚代码；唯一约束可保留或手动删除，不影响现有功能。
