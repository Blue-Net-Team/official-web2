## Context

项目采用预签名直传模式上传文件，流程为 `prepare-upload` → 前端直传 OSS → `confirm-upload`。此过程中会产生三类孤儿数据：
- `PENDING` 超时：用户获取预签名 URL 后未在有效期内完成上传确认
- `REJECTED` 残留：`confirm-upload` 校验失败（MD5/大小/魔数不匹配）后，数据库记录残留
- `ACTIVE` 无引用：业务更新后旧文件不再被任何表引用（如更换头像后旧头像文件）

当前项目无任何定时任务机制，`tb_file` 表缺乏自动清理能力。对象存储使用 MinIO / 阿里云 OSS，采用单 bucket 模型，文件 key 格式为 `{fileType}/{filename}`。

## Goals / Non-Goals

**Goals:**
- 每天自动扫描并清理 `tb_file` 中的孤儿文件记录
- 同步删除对应的对象存储对象，释放存储空间
- 误删风险可控，单条失败不影响整体任务
- 执行时间可通过配置调整

**Non-Goals:**
- 不修改现有文件上传/下载的业务逻辑
- 不引入 Quartz 等外部调度框架（Spring `@Scheduled` 足够）
- 不处理判题独立 bucket（`bluenet-judge`）的资源
- 不为文件添加引用计数等反范式字段

## Decisions

**1. 使用 Spring `@Scheduled` 而非 Quartz**
- **理由**：任务逻辑简单（单方法、无状态），无需持久化、集群协调或动态调度。`@Scheduled` 零依赖，配置即开箱即用。
- **替代方案**：Quartz 可提供持久化和集群锁，但引入额外复杂度，对本场景过度设计。

**2. 使用 SQL JOIN 查询孤儿文件，而非应用层多表查询**
- **理由**：引用检查涉及 12 个业务字段，应用层逐个查询需要 12+ 次数据库往返，代码分散且极易遗漏。单条 JOIN SQL 逻辑集中、可维护性高。
- **替代方案**：应用层循环查询 + 内存求差集。已排除，代码量与风险均高于 JOIN。
- **风险缓解**：此任务为离线定时任务，执行于凌晨低峰期，JOIN 性能不敏感。

**3. 删除顺序：先数据库记录，后 OSS 对象**
- **理由**：如果先删 OSS 后删 DB，OSS 删除成功但 DB 事务回滚会导致记录指向不存在的对象。先删 DB 保证数据一致性，OSS 残留对象可通过后续任务重试清理。
- **替代方案**：事务内同时删除。已排除，OSS 删除为外部 IO，不适合纳入数据库事务。

**4. 单条异常隔离**
- **理由**：某个文件的 OSS 删除失败（如网络抖动）不应导致整个任务中断。try-catch 逐条处理，失败仅记录日志。

**5. 为 `tb_file` 新增 `created_at` 字段**
- **理由**：当前表结构缺少记录创建时间，PENDING 超时清理无法判定文件何时产生。必须通过 Flyway 迁移补齐。旧记录使用 `DEFAULT NOW()` 填充，虽不够精确，但旧数据要么是 ACTIVE（受引用检查保护不会被误删），要么是已有孤儿（反正要清理），故不影响正确性。
- **替代方案**：在 `prepareUpload` 时把创建时间写入独立表或 Redis。已排除，引入额外存储和维护成本，不如直接扩展主表。

**6. PENDING 超时阈值设为预签名有效期 + 缓冲期**
- **理由**：预签名有效期配置为 15 分钟（`storage.presignedUploadExpiry`）。加上 1 小时缓冲，总共 75 分钟。足够覆盖网络延迟和前端处理时间，又避免正常进行中的上传被误删。

## Risks / Trade-offs

- **[风险] 并发场景下误删正在使用的新文件** → **缓解**：在 PostgreSQL READ COMMITTED 隔离级别下，`prepareUpload` / `confirmUpload` 与清理任务的事务隔离保证未提交数据互不可见。若业务在同一事务内完成文件插入和引用更新，不会出现中间状态被误判。
- **[风险] 业务代码新增文件引用字段后，清理任务遗漏检查** → **缓解**：清理 SQL 的引用检查字段必须显式列出。新增引用文件的业务变更时，需同步维护孤儿文件清理的引用检查列表。建议在代码审查清单中增加此项检查。
- **[风险] OSS 对象删除失败导致存储泄漏** → **缓解**：DB 记录已清理，OSS 对象变为无引用的"幽灵对象"。由于对象存储成本较低，且下次任务会重试删除（REJECTED 场景），泄漏量可控。可后续增加存储桶生命周期策略兜底。
- **[权衡] 每天只执行一次，PENDING 文件可能积压近 24 小时** → **接受**：用户明确数据积压无影响，正确性优先于及时性。
