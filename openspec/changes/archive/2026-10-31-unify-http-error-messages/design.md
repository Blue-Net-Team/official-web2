## Context

前端通过 `src/frontend/src/apis/client.ts` 创建 `apiClient` 和 `publicClient`。基础拦截器目前只转换超时错误；`apiClient` 仅在 HTTP 成功响应中处理业务 `code >= 400` 并提示，而 HTTP 4xx/5xx 会原样拒绝。多个页面、密码流程和 `authStore` 因而各自读取 `error.response.data.msg` 或直接展示 `error.message`，产生英文 Axios 错误、裸状态码和重复 Toast。

本次变更将“API 错误消息解析与用户提示”收敛到请求层，页面保留业务流程职责。现有后端 `ResponseMessage` 结构不变，Ant Design 静态 `message` API 已在请求层使用。

## Goals / Non-Goals

**Goals:**

- 所有经过 Axios 客户端的失败请求均只显示一次可读的中文错误提示。
- 后端非空 `ResponseMessage.msg` 优先于所有默认文案。
- 常见 HTTP 状态码、超时、无响应和未知错误均有稳定兜底。
- 保留原始错误拒绝、401 跳转及页面加载状态清理行为。
- `apiClient` 与 `publicClient` 的提示规则一致，SSR 不触发浏览器消息 API。

**Non-Goals:**

- 不修改后端异常消息、HTTP 状态码或响应包装。
- 不将原生 `fetch`、XHR 直传或 SSE 请求迁移到 Axios。
- 不重写页面错误边界、表单本地校验或成功提示。
- 不为支持消息上下文而重构全局 Ant Design Provider；沿用当前静态 `message` 封装。

## Decisions

### 1. 在共享基础客户端中集中处理错误

在 `createBaseClient()` 的响应拒绝分支统一解析 HTTP 错误并调用 `message.error()`，使两个客户端自动获得一致行为。HTTP 成功但业务 `code >= 400` 的处理也下沉为可复用逻辑，避免只在 `apiClient` 生效。

备选方案是在每个页面调用共享 `getErrorMessage()`；该方案仍依赖开发者记得调用，无法从机制上消除遗漏，因此不采用。

### 2. 使用明确的消息优先级

消息解析顺序固定为：

1. 响应体中去除首尾空白后非空的 `ResponseMessage.msg`。
2. HTTP 状态码对应的中文默认文案；业务错误使用响应体 `code`，传输错误使用 `error.response.status`。
3. 超时、无 HTTP 响应的网络异常专用文案。
4. `请求失败，请稍后重试` 作为最终兜底。

状态码表至少覆盖：400、401、403、404、405、408、409、413、415、422、429、500、502、503、504。未收录状态码使用最终兜底，不直接展示 Axios 英文消息或裸状态码。非 JSON、空响应体和结构异常响应均安全进入兜底流程。

### 3. 提示与错误传播分离

拦截器完成提示后仍返回 `Promise.reject(error)`，不改变 service、Store 和 Hooks 的成功/失败控制流。保留原始 Axios 错误及其响应元数据供调试和特殊控制流使用；用户可读性由集中提示保证，不要求用普通 `Error` 替换 `AxiosError`。

401 在统一提示后继续执行现有登录跳转。浏览器环境判断集中在提示函数中，SSR 只拒绝错误，不调用 `message`。

### 4. 页面不再重复提示 API 错误

清理页面和 Store 中针对 Axios/API 失败的 `message.error()` 及仅为该目的存在的消息提取代码。`catch` 可继续恢复 loading、阻止成功跳转或保存错误状态，但不得再次弹出同一 API 错误。

保留以下页面职责：

- 输入为空、密码不一致等本地校验提示。
- 上传前文件格式和大小校验。
- 非 Axios 请求自己的错误提示。
- 成功消息和成功后的导航、刷新。

### 5. 先自动化验证请求层，再验证关键链路

为消息优先级、状态码表、空/非 JSON 响应、网络错误、SSR 和拒绝语义建立聚焦测试；如当前前端没有测试运行器，可添加仅开发环境使用的轻量测试配置。随后通过现有前端服务进行 Playwright 验证，确认登录和代表性管理/公开请求只出现一次正确消息。

## Risks / Trade-offs

- [清理页面提示不完整会产生双重 Toast] → 按 API 错误提示模式全局检索，并在关键链路验证单次提示。
- [统一自动提示会让原本静默的公开接口或后台轮询出现 Toast] → 盘点这些调用；确有静默需求时使用显式、局部的跳过提示机制，而不是默认全局豁免。
- [HTTP 200 业务错误与传输错误的来源不同] → 分别使用 `response.data.code` 和 `error.response.status`，并覆盖两类测试。
- [替换错误类型会破坏现有 `instanceof AxiosError` 分支] → 保留原错误对象，仅集中展示消息。
- [静态 Ant Design 消息不完全继承 App 上下文主题] → 本次沿用现有行为，将上下文统一留作独立改进。

## Migration Plan

1. 建立错误文案与解析/提示测试，再实现共享拦截器逻辑。
2. 移除 Store、密码流程和页面中的重复 API 错误提示，保留本地校验和状态处理。
3. 执行前端静态检查、请求层测试和构建检查。
4. 使用现有 3000 端口服务或按项目约束启动服务，通过 Playwright 验证后端有消息、无消息及网络失败场景。

回滚时可恢复共享拦截器和页面提示文件；无数据库、接口或配置迁移。

## Open Questions

无。默认采用“所有 Axios API 错误统一提示”的策略；实施中若发现必须静默的后台请求，再针对该调用记录并评审例外。
