## 背景

BlueNet后端目前缺乏HTTP API调用的请求级日志记录。虽然存在用于业务操作的审计日志，但没有简单机制在控制层处理完成后记录基本的HTTP请求信息。本次变更采用最简单的实现方式：使用HandlerInterceptor在请求处理完成后记录方法、URI和响应状态码，格式为`GET /api/v1/... 200 OK`。

## 目标 / 非目标

**目标:**
1. 在控制层处理完成后记录每个HTTP请求的端点路径、HTTP方法和响应状态码
2. 使用简单的日志格式：`{方法} {URI} {状态码} {状态文本}`
3. 集成到现有的Spring Boot日志框架中

**非目标:**
1. 记录请求/响应体
2. 复杂的环境特定配置
3. 性能优化或高级功能
4. 日志存储到数据库

## 决策

1. **拦截器 vs 过滤器**: 使用 `HandlerInterceptor` 的 `afterCompletion` 方法进行请求日志记录。拦截器在控制层处理完成后执行，可以准确记录最终响应状态。`afterCompletion` 方法在视图渲染完成后调用，适合记录请求的完整处理结果。

2. **日志框架**: 使用 SLF4J 与 Logback（Spring Boot 默认），使用 INFO 级别记录日志。

3. **日志格式**: 简单的人类可读格式：`{HTTP方法} {请求URI} {响应状态码} {状态文本}`，例如：`GET /api/v1/users 200 OK`。

4. **记录的信息**:
   - 请求: HTTP 方法、请求 URI（完整路径）
   - 响应: HTTP 状态码和状态文本

5. **敏感数据保护**: 不记录请求体，避免记录敏感信息。查询参数保留在 URI 中，但不在日志中特殊处理。

6. **配置**: 简单启用/禁用开关，无需复杂的环境特定配置。

7. **实现**: 尽可能简单，不添加额外的性能优化或复杂功能。

## 风险 / 权衡

**风险:**
1. **性能影响**: 记录每个请求会增加少量开销 → 缓解措施: 使用简单的日志实现，避免复杂处理
2. **敏感数据泄露**: 可能记录包含敏感参数的URI → 缓解措施: 避免记录请求体，URI中的参数被视为可接受风险

**权衡:**
1. **简单性 vs 功能完整性**: 选择最简单的实现，牺牲高级功能如环境特定配置和性能优化
2. **开发便利性 vs 安全性**: 简单日志格式便于开发调试，但可能包含敏感查询参数

## 迁移计划

1. **开发阶段**: 实现拦截器，本地测试
2. **测试**: 基本功能测试验证日志输出格式
3. **部署**: 部署到开发和生产环境
4. **回滚策略**: 如果出现问题，移除拦截器注册

## 开放问题

1. 是否应该为不同的响应状态码使用不同的日志级别？（例如：成功用INFO，错误用WARN）
2. 是否应该排除某些端点（如健康检查）以减少日志噪音？
