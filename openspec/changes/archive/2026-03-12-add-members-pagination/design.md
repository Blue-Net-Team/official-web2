## Context

当前成员列表页面 (`/members`) 使用服务端组件一次性获取所有成员数据，然后传递给客户端组件 `Members` 进行展示。后端已提供分页接口 `GET /api/v1/members?page={page}&size={size}&direction={direction}`，前端服务层 `MemberService.getMemberList` 也已支持分页参数。

当前架构：
- 页面组件 (`page.tsx`) 是服务端组件，负责数据获取
- `Members` 组件是客户端组件，负责筛选和展示
- 使用 `limit` prop 控制显示数量（目前未使用分页）

## Goals / Non-Goals

**Goals:**
- 实现前端分页功能，每页显示16个成员
- 保持方向筛选功能与分页的兼容
- 使用 antd Pagination 组件保持 UI 一致性
- 页面切换时平滑滚动到顶部

**Non-Goals:**
- 不修改后端接口（后端已支持分页）
- 不实现无限滚动加载
- 不实现搜索功能

## Decisions

### 1. 分页组件位置

**决定**: 将分页逻辑放在 `Members` 客户端组件内部

**理由**:
- 筛选和分页是紧密耦合的功能
- 客户端状态管理更简单，避免服务端组件与客户端组件之间的复杂交互
- 方向筛选时需要重置到第一页

**替代方案**: 将分页状态提升到页面组件
- 缺点：需要将筛选状态也提升，增加复杂度
- 优点：可以利用 Next.js 的路由参数实现 URL 分页

### 2. 数据获取策略

**决定**: 改为客户端获取数据

**理由**:
- 分页和筛选需要在客户端响应式处理
- 避免每次翻页都需要服务端渲染
- 使用 React Query 或 SWR 可以实现更好的缓存和加载状态

**替代方案**: 保持服务端获取，使用 URL 参数
- 缺点：每次翻页都需要页面刷新，用户体验差

### 3. 分页组件选择

**决定**: 使用 antd Pagination 组件

**理由**:
- 项目已使用 antd 作为 UI 库
- Pagination 组件功能完善，支持页码、快速跳转等
- 样式与项目风格一致

## Risks / Trade-offs

**[SEO 影响]** → 分页内容对 SEO 不友好
- 缓解：首屏使用服务端渲染，后续分页使用客户端渲染

**[首次加载时间]** → 改为客户端获取可能增加首屏加载时间
- 缓解：使用 loading 状态和骨架屏优化用户体验

**[筛选与分页冲突]** → 切换筛选时当前页码可能超出范围
- 缓解：切换筛选时自动重置到第一页
