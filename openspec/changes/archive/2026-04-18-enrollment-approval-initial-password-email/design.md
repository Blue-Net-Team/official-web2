## 背景

当前管理员通过报名审核时，流程会把记录状态改为 `APPROVED`，并在需要时创建 `tb_user`。但首次登录所需的凭据发放仍不完整：审核通过后不一定会把邮箱/密码可靠写入用户表，也不会向通过者发送“初始密码”通知邮件。现有登录语义要求：前端先对明文密码做 SHA-256，再把结果提交给后端，由后端与数据库中的 BCrypt 值比对。

代码现状：
- 已有异步邮件发送能力（`EmailSender.sendHtmlAsync`）以及硬编码 HTML 模板模式。
- 审核通过主流程在 `EnrollDomainServiceImpl`。
- 重置密码/验证码等流程已经体现了稳定的密码更新与邮件发送模式。

约束：
- 必须兼容当前登录约定（前端提交 SHA-256 后的密码值）。
- 不破坏“已存在用户”的审核通过路径。
- 本次迭代优先小步落地；模板系统虽有数据库能力，但业务流当前主要仍是硬编码模板。

## 目标 / 非目标

**目标：**
- 审核通过且创建新用户时，确保 `tb_user.email` 与 `tb_user.password` 一定落库。
- 生成 8 位随机初始密码。
- 按既有契约保存密码：先 `SHA-256`，再 `BCrypt` 后持久化。
- 新建用户时异步发送审核通过邮件，邮件中包含“哈希前明文初始密码”。
- 若审核命中已存在用户，保持现有行为（不重置密码、不重发初始凭据邮件）。

**非目标：**
- 本次不引入数据库模板驱动的消息渲染。
- 本次不做批量补发/后台重试面板。
- 本次不改前端登录交互与接口契约。

## 方案决策

### 1. 在审核通过领域路径内完成凭据发放
- 决策：在 `EnrollDomainServiceImpl.approveEnrollment` 的“新建用户”分支中实现初始密码生成、哈希、落库与通知触发。
- 原因：审核通过是账号授予的权威时点；把逻辑集中在领域路径可避免跨层分裂与状态不一致。
- 备选：放到 `EnrollServiceImpl` 在领域调用后再补处理。否决，因为核心分支与状态不变量已在领域层。

### 2. 密码处理管线固定为 SHA-256 -> BCrypt
- 决策：生成明文初始密码后，先算 `sha256(plaintext)`，再 `passwordEncoder.encode(sha256Value)` 存库。
- 原因：与当前学号登录契约完全兼容，不引入前后端协同改造。
- 备选：直接 `BCrypt(plaintext)`。否决，因为会破坏现有登录输入语义。

### 3. 本期继续使用硬编码审核通过邮件模板
- 决策：沿用既有做法，在审核通过流程新增一份硬编码 HTML 模板，并通过 `sendHtmlAsync` 异步发送。
- 原因：改动面小、风险低、可快速补齐 onboarding 缺口。
- 备选：本次同步切到 DB 模板读取。否决，因为当前业务流并未普遍接入该机制，范围会显著扩大。

### 4. 已存在用户分支保持非破坏性
- 决策：若学号已存在对应用户，审核通过时不生成新密码、不改旧密码、不发送初始密码邮件。
- 原因：避免意外改密导致账号被锁或用户困惑，保证幂等与可预期。
- 备选：每次审核通过都轮转密码并重发。否决，运维风险高。

## 风险与权衡

- 风险：明文初始密码通过邮件发送，邮箱被盗时存在泄露面。  
  缓解：邮件内增加“首次登录后立即改密”提示；避免在日志中输出明文。
- 风险：异步发送失败会出现“审核已通过但用户未收到密码”。  
  缓解：审核主流程不回滚，同时确保失败可观测（日志/告警）并支持人工补救。
- 风险：若 SHA-256 处理实现分散，可能出现不一致。  
  缓解：复用或集中封装哈希逻辑，与现有系统用户密码约定保持一致。
- 风险：审核路径逻辑增加导致回归风险。  
  缓解：补齐新建用户/已存在用户双分支单测与集成验证。

## 迁移计划

1. 在不改变现有 API 契约前提下，落地审核通过的凭据发放与通知。
2. 部署后在测试环境验证：
   - 审核通过一个未建号学号报名；
   - 校验 `tb_user.email/password` 已按规则持久化；
   - 使用邮件中的初始密码完成登录；
   - 校验已存在用户分支行为不变。
3. 回滚策略：回退本变更，审核流程恢复到原先行为（仅无初始密码邮件）。
