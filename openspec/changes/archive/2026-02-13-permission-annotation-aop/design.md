## Context

当前项目采用 Spring Boot + JWT，权限控制依赖角色与权限的关系表。需要引入注解驱动的权限定义与扫描同步机制，减少手工维护成本，并提供统一的访问控制入口。现有文件访问权限依赖业务层判断，不能用简单的权限注解替代。权限 value 采用 user:create 格式并要求强校验。无注解接口默认拒绝访问，但应用仍可启动。

## Goals / Non-Goals

**Goals:**
- 引入 `@Permission` 注解和 AccessLevel 访问级别，实现统一权限入口。
- 启动时扫描注解并同步权限表，批量处理并物理删除幽灵数据。
- AOP 进行权限校验，支持 PUBLIC/AUTHENTICATED/PROTECTED 逻辑。
- 引入 CANDIDATE 角色，保证用户角色不为空。
- 业务层保留文件权限的动态判断。

**Non-Goals:**
- 不实现多租户权限隔离。
- 不做分布式权限缓存或跨服务权限中心。
- 不在注解层表达复杂业务规则（方向/年级等），继续由业务层校验。

## Decisions

1. **注解作为权限唯一来源**
   - 选择理由：保证代码与权限表一致，减少手工维护。
   - 备选：数据库配置为主，代码不标注权限。缺点是开发体验差，易遗漏。

2. **AccessLevel 三段式访问控制**
   - PUBLIC/AUTHENTICATED/PROTECTED 明确区分开放、登录、权限访问。
   - 备选：仅使用 PROTECTED + 业务层判断。缺点是登录接口和公开资源处理复杂。

3. **扫描器物理删除幽灵数据**
   - 选择理由：保持权限表与代码一致，避免历史残留权限。
   - 备选：软删除。缺点是残留会干扰权限管理与分配。

4. **无注解接口默认 403，但不阻止启动**
   - 选择理由：提升安全性，避免遗漏权限；同时不影响启动流程。
   - 备选：默认公开。缺点是风险较高。

5. **文件接口保持业务层权限判断**
   - 选择理由：文件访问权限依赖文件类型、方向和用户关系，注解无法表达。
   - 备选：引入注解条件表达式。缺点是复杂度高，难维护。

6. **RBAC 角色层级策略**
   - SUPER_ADMIN > DIRECTION_ADMIN > MEMBER > CANDIDATE
   - 选择理由：匹配业务角色层级，简化权限继承与校验。

## Risks / Trade-offs

- [风险] 物理删除导致回滚时权限缺失 → [缓解] 发布前确保权限扫描与角色绑定脚本同步，必要时提供恢复脚本。
- [风险] 无注解接口被拒绝导致功能不可用 → [缓解] 在开发测试阶段启用权限扫描日志与接口清单校验。
- [风险] 权限 value 校验过严影响快速迭代 → [缓解] 统一命名规范与校验规则，提供错误提示。
- [风险] 扫描启动耗时增加 → [缓解] 批量查询与批量写入，控制扫描范围。

## Migration Plan

1. 引入 `@Permission` 注解、AccessLevel 枚举与校验规则。
2. 实现 PermissionScanner 扫描并同步权限表，启用物理删除策略。
3. 实现 PermissionAspect 统一拦截与权限校验。
4. 增加全局无注解拦截（/api/** 默认 403），配置白名单登录接口。
5. 初始化角色数据，新增 CANDIDATE 角色。
6. 为现有受保护接口补充 `@Permission` 注解并分配角色权限。
7. 灰度验证关键接口（登录、文件访问、考核相关接口）。
8. 上线后监控权限拒绝日志，补齐遗漏权限。

## Open Questions

- 是否需要在权限表中保存模块信息（用于后台分组展示）？
- 是否提供权限刷新管理接口（不重启更新缓存）？
