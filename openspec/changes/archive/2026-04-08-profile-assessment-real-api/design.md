## Context

**背景**：
- 个人主页的"我的考核"部分当前使用 mock 数据（`MockProfileService.getAssessments()`）
- 后端考核 API 已基本完成，包括考核时间查询、进度查询、会话管理等接口
- 前端已有部分考核相关的 API 服务（`assessmentTimeService`、`assessmentSessionService`、`assessmentQuestionService`）
- 需要将 mock 数据切换到真实 API，实现数据的实时更新

**当前状态**：
- Mock 数据硬编码在 `src/frontend/src/mocks/data/profile.ts`
- 考核列表组件 `AssessmentList` 已实现，依赖 `Assessment` 类型
- 后端 API 返回 `AssessmentTimeDTO`，包含考核时间、进度等基础信息
- 限时考核需要额外调用会话接口获取截止时间

**约束**：
- 保持现有的 UI 组件和交互逻辑不变
- 确保数据类型与后端 DTO 一致
- 处理加载状态和错误状态
- 考核状态需要根据当前时间动态计算

## Goals / Non-Goals

**Goals:**
- 实现考核时间列表的真实 API 调用
- 实现考核进度的实时查询
- 实现限时考核的会话管理（截止时间获取）
- 将后端数据转换为前端 `Assessment` 类型
- 根据时间范围动态计算考核状态
- 移除 mock 数据依赖

**Non-Goals:**
- 不修改考核列表的 UI 展示逻辑
- 不修改考核详情页面（后续变更处理）
- 不修改后端 API 接口
- 不处理考核答题功能（已有独立页面）

## Decisions

### 1. 数据获取策略

**决策**：采用并行请求策略，先获取考核时间列表，再并行获取每个考核的进度和会话信息

**理由**：
- 考核时间列表接口已包含基础的进度信息（`totalQuestions`、`completedQuestions`）
- 限时考核的截止时间需要单独调用会话接口
- 并行请求可以减少总请求时间

**替代方案考虑**：
- 方案 A：仅使用考核时间列表接口，不获取会话信息
  - 缺点：无法展示限时考核的剩余时间
- 方案 B：创建聚合接口，一次性返回所有数据
  - 缺点：需要修改后端 API，增加复杂度

### 2. 考核状态计算

**决策**：在前端根据当前时间和考核时间动态计算状态

**状态判断逻辑**：
- `not-started`：当前时间 < `startTime`
- `in-progress`：`startTime` ≤ 当前时间 ≤ `endTime`（或限时考核的 `deadline`）
- `ended`：当前时间 > `endTime`（或限时考核的 `deadline`）

**理由**：
- 状态是时间相关的动态数据，前端计算可以实时响应
- 减少后端接口复杂度
- 便于处理限时考核的特殊逻辑

### 3. 数据处理位置

**决策**：在页面组件中处理数据转换，不创建新的服务层

**理由**：
- 数据转换逻辑相对简单
- 避免过度抽象
- 便于调试和维护

**替代方案考虑**：
- 方案 A：在 `assessmentTimeService` 中添加转换方法
  - 缺点：服务层职责过重，混合了 API 调用和数据转换
- 方案 B：创建独立的 `profileAssessmentService`
  - 缺点：增加文件数量，当前场景过于简单

### 4. 错误处理

**决策**：采用静默失败策略，仅在控制台输出错误信息

**理由**：
- 考核数据不是核心功能，加载失败不应影响页面其他部分
- 保持与现有代码风格一致
- 后续可根据需要添加错误提示 UI

## Risks / Trade-offs

**[风险] 并行请求数量过多** → **缓解**：限制考核时间列表的分页大小（默认 20 条），实际场景中用户的考核数量通常较少

**[风险] 时间计算时区问题** → **缓解**：后端返回 ISO 格式时间字符串，前端使用 `dayjs` 统一处理时区转换

**[风险] 限时考核截止时间计算复杂** → **缓解**：直接复用后端会话接口返回的 `deadline`，不在前端计算

**[权衡] 数据一致性**：考核状态在前端计算，可能与后端略有延迟 → **接受**：状态判断基于时间戳，误差在可接受范围内

**[权衡] 移除 mock 服务**：可能导致其他依赖 mock 的代码失败 → **缓解**：仅移除考核相关的 mock，保留其他 mock 数据
