## Why

API 与 Judge 当前的 JVM 参数和容器内存上限尚未经过真实业务负载验证，无法判断现有配置在报名、文件考核和 Python 算法判题峰值下是否稳定。需要建立可重复、可比较的压测与内存观测能力，为后续 `Xms`、`Xmx`、GC、消费并发和容器 limit 调优提供依据，而不是凭空闲内存或单次 `docker stats` 结果做决策。

## What Changes

- 新增基于 k6 的压测脚本与统一运行配置，覆盖三个初始独立执行的场景：公开报名、5 分钟 200 个完整上传答题人次的考核文件上传，以及多道算法题上的 Python 运行与正式提交判题。
- 提供隔离压测环境的重置流程：清理上一轮数据后重启 API，由 Flyway 重建数据库结构，并由现有系统用户初始化器恢复管理员；不手写 SQL 操作业务表。
- 通过现有业务 API 初始化学院、测试考生、考核轮次、文件上传题、算法题及判题资产，生成包含动态 ID 和用户池的统一测试上下文。
- 为认证场景维护测试用户与虚拟用户的稳定一对一分配，逐 VU 登录并复用 Cookie/CSRF，避免同账号登录相互撤销 Token。
- 增加业务正确性校验与异步判题完成跟踪，分别统计多道算法题的运行/提交结果及 run/formal 队列，避免仅创建任务、上传失败或重复提交被误算为有效负载。
- 增加 API/Judge 容器与 JVM 指标的时序采集和实验记录，覆盖空闲基线、预热、稳定压力、停止压力后的回收阶段。
- 固化可重复实验方法与结果模板，使不同 JVM 参数能够在相同负载下比较；本轮只提供调优依据，不直接承诺或批量应用最优参数。
- 不使用 Playwright，不压测前端页面，不增加 JWT/CSRF 绕过机制，不在生产环境执行压测。

## Capabilities

### New Capabilities

- `java-service-memory-load-testing`: 定义可重复的压测环境重置、API 数据初始化、测试用户隔离、报名/文件考核/Python 判题负载，以及 API/Judge 内存观测和实验报告要求。

### Modified Capabilities

无。本变更新增测试与观测能力，不改变现有业务接口的外部需求。

## Impact

- 新增压测脚本、初始化/重置编排、指标采集脚本、运行配置与结果文档；具体目录在 `design.md` 中确定。
- 使用现有公开及管理 API、MinIO 预签名直传、RabbitMQ 判题链路和 Judge 真实 Python/isolate 执行流程。
- 引入 k6 作为压测执行工具；JVM/容器指标采集复用现有 JDK、Docker 与服务能力，Python 命令行编排额外使用 Click（`>=8.1,<9`）。
- 影响隔离测试环境中的 PostgreSQL、Redis、RabbitMQ、MinIO、API 和 Judge 数据及运行状态；不得指向生产或共享环境。
- 不改变业务 DDD 分层、权限规则、前端 ISR、生产 API 契约或现有部署拓扑。
