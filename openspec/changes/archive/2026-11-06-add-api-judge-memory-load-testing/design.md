## Context

API 与 Judge 默认均使用 `-Xms64m -Xmx384m -XX:+UseSerialGC`，Compose 内存上限已对齐为 1g，但现有证据只覆盖启动和空闲状态。本次需要建立真实业务负载下的可重复实验，而不是以健康检查或人工观察一次 `docker stats` 代替容量验证。

已确认的技术约束：

- 只使用 k6 和基础设施/JVM 观测工具，不使用 Playwright。
- 业务基础数据通过现有 API 创建，不直接执行 SQL；清库后重启 API，由 Flyway 与 `SystemUserInitializer` 恢复数据库和系统管理员。
- 当前 JWT 过滤器还会校验 Redis Token 白名单和数据库用户，不存在也不新增调试 KEY 绕过认证。
- 文件内容通过预签名 URL 直传 MinIO，API 只处理 prepare/confirm 和答案提交。
- Judge 的业务压力来自 API 创建任务、RabbitMQ 投递和 Judge 异步消费；健康检查不构成判题负载。
- 同一用户重新登录会撤销旧 Token，因此认证压测必须隔离用户会话。

## Goals / Non-Goals

**Goals:**

- 提供报名、文件考核、Python 算法三个可独立执行的 k6 场景；文件基线为 5 分钟 200 个完整上传答题人次，算法基线覆盖多道题的运行与正式提交。
- 提供明确且带防误操作保护的环境重置、API 初始化、单用户预跑和分阶段压测流程。
- 生成动态测试上下文，包含用户池、考核 ID、题目 ID 和场景配置，不依赖硬编码生产数据。
- 同时采集 k6 业务结果、Docker 容器内存和 JVM 指标，并按统一时间线保存。
- 支持固定镜像、固定数据、固定负载下仅改变一个 JVM/运行时参数的对照实验。
- 区分 JVM 堆回收与容器 RSS 回落，同时覆盖 Judge 的 Python/isolate 子进程内存。

**Non-Goals:**

- 不测前端、SSR、浏览器体验或静态资源。
- 不修改业务 API 契约，不新增认证绕过，不直接调 SQL 初始化或清理业务表。
- 不在生产或共享环境执行，不自动对生产配置应用调优结果。
- 不在首轮混合三个场景，不以压垮服务为默认目标，不承诺最终 QPS 或生产容量。
- 不将 MinIO/PostgreSQL/RabbitMQ 自身调优、AI 服务、邮件和 GitHub 外部调用纳入本轮。

## Decisions

### 1. 使用独立 `src/load-test/` 目录承载全部压测资产

规划结构如下，实施时可按脚本职责拆分，但不将压测代码混入后端业务模块：

```text
src/load-test/
├── README.md                 # 前置条件、危险操作说明、执行步骤
├── config/                   # 非密钥场景配置与基线负载
├── lib/                      # HTTP、认证、CSRF、校验、用户分配等公共逻辑
├── setup/                    # 环境重置与 API 初始化编排
├── scenarios/
│   ├── enrollment.js
│   ├── assessment-file-upload.js
│   └── algorithm-python.js
├── monitoring/               # 容器/JVM 指标采样与阶段标记
└── results/
    ├── README.md             # 结果格式和实验元数据说明
    └── ...                   # 本地生成结果，不提交敏感数据或大文件
```

选择 k6 是因为三个场景均为 HTTP 驱动，且 `setup()` 可以返回动态上下文。环境重建属于 Docker/Compose 编排，不勉强由 k6 完成；业务初始化则由 k6 `setup()` 调用现有 API 完成。Python 编排、重置、监控和报告入口统一使用 Click 注解声明参数，依赖由 uv 管理，声明在 `src/load-test/pyproject.toml`，锁定文件为 `uv.lock`。

### 2. 环境级重置与业务级初始化分离

环境重置只允许在本机明确批准的 Compose 目标执行。当前用户已明确授权使用并清空现有本地 `bluenet` / `ENV=dev` 环境；同时保留独立 `bluenet-loadtest` / `loadtest` 目标作为后续隔离选项。重置依次处理 PostgreSQL、Redis、RabbitMQ、MinIO 的上一轮状态，再启动 API/Judge。PostgreSQL 必须处于空库状态后启动 API，使 Flyway 完整迁移；API 启动后由 `SystemUserInitializer` 创建系统管理员。

重置入口必须同时满足：

- 配置指向本地且明确允许的 Compose 项目/ENV 组合；
- 操作者显式设置破坏性操作确认变量；
- 输出将删除的环境标识并拒绝生产地址/默认共享配置；
- 重置后等待 API、Judge 及依赖健康，而不是固定 sleep 后立即发请求。

不通过逐个业务 DELETE 接口实现环境重置，因为这会遗留对象、队列和系统数据。重置过程不手写 SQL。

### 3. k6 `setup()` 通过真实 API 创建统一上下文

初始化使用系统用户配置对应的账号正常登录，复用现有密码 SHA256 规则。管理员会话用于创建：

1. 学院及必要基础资料；
2. 数量覆盖场景最大 VU 的 CANDIDATE 用户；
3. 时间窗口覆盖整个实验、方向/年级匹配的考核轮次；
4. 一道文件上传题；
5. 可配置数量的多道 Python 算法题，以及每道题独立的判题配置、标准解、生成器和测试数据；
6. 每道算法题运行与正式提交所需的 Python 语言资源限制。

算法配置通过现有管理 API 保存并请求测试数据生成，然后等待生成完成和队列排空。所有异步初始化完成后才返回上下文：

```text
{
  runId, baseUrl, storagePublicUrl,
  users[{id, studentId, password, direction, assessmentGradeYear}],
  assessmentTimeId, fileQuestionId, algorithmQuestionIds[],
  workload, fileFixture, pythonFixtures[]
}
```

密码和 Token 不写入提交到仓库的结果。若现有接口不能完整表达某项初始化，实施时必须先记录缺口并讨论最小补充方式，不能悄悄退回 SQL。

### 4. 认证用户使用一对一分配和逐 VU 会话

文件与算法场景按稳定 VU 编号领取固定用户，用户池小于最大 VU 数时在初始化阶段失败，不循环复用。每个 VU 第一次迭代正常登录，后续复用本 VU 的 Cookie Jar 与 CSRF Token。

状态修改请求统一从当前会话附加 `X-CSRF-Token`。登录、prepare、confirm、答案提交、算法提交和轮询分别打标签，以便定位内存对应的业务阶段。报名场景不需要用户池，但每条新报名使用 `runId` 与全局迭代标识生成唯一学号，并仅将 201 新建成功计入有效报名。

### 5. 三个场景使用真实、可校验的业务闭环

**报名**：只调用 `POST /api/v1/enrollments`，首轮仅测新建，不混入冲突和 `forceUpdate` 更新。采用可配置到达速率与总量，响应同时校验 HTTP 201 和业务响应。

**文件考核**：正式计时前完成考生登录，每个人次完成 prepare-upload → 预签名 PUT 到 MinIO → confirm-upload → 提交或更新答案。基线在 5 分钟内均匀启动 200 个完整流程，即平均 40 人次/分钟、约 0.667 人次/秒，而不是 200 并发或 200 QPS；可用每 3 秒启动 2 个迭代表达该到达速率。200 人次只统计完整成功闭环，登录不计入正式人次。固定文件类型、大小和内容生成方式，首轮采用小文件；首次提交与后续更新分别打标签，409/403/CSRF 失败不计入有效人次。MinIO PUT 和 API 请求分别计时，避免把对象存储耗时误认为 API 延迟。

**Python 算法运行与提交**：初始化可配置数量的多道算法题，首轮按固定规则将任务均匀分配到各题，并分别记录每题结果。每个 VU 使用固定、轻量、确定性的 Python 源码，既覆盖 `/algorithm-judge/run` 不计分运行，也覆盖 `/algorithm-judge/submit` 保存答案并正式判题；两类操作分别进入 run/formal 队列、保存各自的 `jobId` 并轮询至终态。一个 VU 同时最多保留一个未终态任务，以限制首轮队列积压。按题目和操作类型记录任务创建速率、完成速率、终态结果、端到端时长和轮询量；仅任务入队不视为运行或判题完成。题目数量及运行/提交比例或总人次必须进入版本化负载配置。

三个场景先分别运行。混合场景只有存在明确峰值模型时另行配置，不作为本轮验收前置条件。

### 6. 固定实验阶段和负载，保证不同参数可比较

每轮实验使用相同镜像、数据规模、源码、文件、测试用例和负载配置，依次执行：

```text
重置与初始化 → 健康等待 → 空闲基线 → 单用户预跑 → 预热
             → 阶梯加压 → 稳定负载 → 停止提交 → 队列排空 → 回收观察
```

默认基线采用保守的小规模参数，实际数值写入版本化场景配置，而不是散落在命令行。每轮只改变一个变量，例如 API `Xmx`、Judge `Xmx` 或 Judge 消费并发。调参对照必须重复相同负载；若出现 OOMKilled、非预期错误或持续失控积压，该轮标记失败，不用于得出容量提升结论。

### 7. 容器指标与 JVM 指标同步采样

监控采样与 k6 同时启动，使用统一 `runId`、时间戳和阶段标记：

- Docker：API/Judge 容器 RSS、limit、CPU、重启/OOM 状态；Judge 容器指标天然包含编译器、Python 和 isolate 子进程。
- JVM：Heap used/committed/max、非堆/直接缓冲区可获取指标、GC 次数/停顿、存活线程数。
- 业务：k6 请求/业务成功率、P95/P99、有效报名数、有效上传与答案数、判题完成数。
- 异步：RabbitMQ run 与 formal 队列各自的 ready/unacked 深度，用于区分稳态与积压，并避免一种操作的队列掩盖另一种操作的堆积。

Judge 已暴露 Actuator metrics；API 仅在隔离压测配置中通过环境变量增加 `metrics` 暴露，并从容器网络/回环地址采集，不新增公网端口。若 API 的 Actuator 安全链要求认证，采集器使用专用管理员会话低频采样，并在结果中记录该固定开销。采样失败必须显式标记，不能用空值拼出完整曲线。

原始结果保存为 CSV 或 JSON，另附实验元数据和汇总。日志、账号、Cookie、Token 与环境密钥不得进入提交的结果文件。

### 8. 结果用于提出调优假设，而非自动调参

报告至少比较空闲、峰值、Full GC 后/压力后稳定值，以及容器 limit 余量。`Heap used` 回落但 RSS 不回落不能直接判定泄漏；需要结合 committed、GC 和后续重复负载判断。Judge 的容器 limit 不能按 `Xmx + 固定值` 推算，必须包含实际子进程峰值。

本轮交付基线结果和可复现实验方法。任何参数建议必须引用对应实验编号；实际调优变更另行评审。

## Risks / Trade-offs

- [环境重置误删共享数据] → 使用本地项目/ENV 白名单、生产地址拒绝和显式破坏性确认；当前仅额外获得用户对本地 `bluenet/dev` 的明确授权，文档首屏标注风险。
- [API 初始化覆盖不了完整判题资产] → 先用单用户预跑验证配置、生成测试数据、语言限制和正式判题；存在缺口时停下来确认，不退回 SQL。
- [初始化任务污染空闲基线] → 等待异步初始化完成、队列排空和内存稳定后再开始基线采样。
- [同账号多 VU 导致 Token 相互撤销] → 用户池容量预检和一对一固定分配。
- [文件预签名 URL 的宿主机地址不一致] → 使用浏览器/压测机实际可访问的 `MINIO_PUBLIC_URL`，单用户预跑验证 prepare/PUT/confirm 全链路。
- [算法轮询压倒 API] → 固定且保守的轮询间隔，单独统计轮询请求，禁止 tight loop。
- [提交速率高于 Judge 消费速率导致失控积压] → 首轮每 VU 仅一个未完成判题任务，记录队列并设置停止条件；积压实验另行设计。
- [监控本身改变内存结果] → 固定采样间隔与认证方式，所有对照实验使用相同监控配置，避免高频 JFR/NMT 作为默认基线。
- [本地 Docker Desktop 与 K8s cgroup/沙箱行为不同] → 结果只代表所测环境，报告记录 OS、Docker、资源和镜像；生产/K8s 结论需在同拓扑环境复测。
- [一次性短时峰值被误认为可持续容量] → 保留稳定阶段与停止后的回收观察，必要时后续增加 soak test。

## Migration Plan

本变更不迁移业务数据，按以下步骤引入：

1. 在隔离 Compose 环境安装/确认 k6，配置专用资源名称与非生产凭据。
2. 新增脚本和配置但默认不执行破坏性重置；先审核环境识别与确认保护。
3. 单用户依次验证报名、文件上传和 Python 正式判题。
4. 启动基线监控，分别运行三个保守负载场景，验证指标和结果完整性。
5. 固化基线后再开展单变量 JVM 对照实验。

回滚只需停止使用压测编排并移除本地压测配置；无需回滚业务数据或 API。若临时 API Actuator 配置通过独立压测 override 注入，移除 override 即恢复默认暴露范围。

## Open Questions

- 首轮基线的具体 VU/到达速率、持续时间和用户池规模，应在实施时根据压测机资源写入保守默认配置，并允许显式覆盖。
- 文件首轮采用的具体大小、Python 算法题数量、各题测试用例规模及运行/提交比例或总人次需在单用户预跑后固定；后续大文件/高内存程序属于独立实验。
- 若现有 API 无法无 SQL 地完成某项初始化，需要用户确认是补充测试专用初始化能力还是调整场景范围。
