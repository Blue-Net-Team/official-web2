## Context

BlueNet 当前考核模块已经具备题目 CRUD、考生查询题目、答案提交和文件上传能力。题目内容通过 `QuestionContent` 多态 JSON 存储，`AlgorithmContent` 已有 `testCases`、`timeLimit`、`memoryLimit` 基础字段，`AssessmentAnswer` 已预留 `language` 字段，但接口和服务尚未使用。

当前缺口集中在两个方向：

- 评判体系缺失：文件上传题需要团队成员以上权限人工评分/评论，单选题、多选题、算法题需要自动评判，方向管理员以上需要基于评判结果控制考生是否通过。
- 算法题执行缺失：标准输入输出代码需要在独立沙盒环境运行，通过队列排队，避免阻塞主业务接口和污染主应用进程。

## Goals / Non-Goals

**Goals:**
- 建立统一的题目级评判结果模型，支持自动评判和人工评判。
- 单选题、多选题提交后立即自动评判，人工只能查看结果，不能改分。
- 文件上传题支持团队成员以上人工评分和评论。
- 算法题支持标准输入输出模式、语言模板、运行、提交、异步判题、沙盒执行和轮询结果。
- 算法题默认运行用例与题面样例分离，允许管理端配置一组专门用于“运行”的系统 testcase。
- 记录客观题通过率统计所需的标准化结果码，支持题目维度查询通过率和算法题 ACM 状态分布。
- 方向管理员以上可以查看汇总结果并控制考生是否通过考核。

**Non-Goals:**
- 本变更不实现 WebSocket/SSE 推送，第一版使用轮询。
- 本变更不支持函数补全型算法题，只支持标准输入输出型。
- 本变更不支持人工修改单选题、多选题、算法题的自动评分。
- 本变更不要求保存算法题每次自定义运行输入的长期历史。
- 本变更不要求第一版提供复杂趋势图、时间序列分析或跨年度统计报表。

## Decisions

### 统一评判模型

引入题目级 `AssessmentJudgement` 概念，所有题型都把结果写入同一类评判记录。自动评判来源为系统，人工评判来源为团队成员或更高权限用户。

备选方案是每个题型各自维护结果表，例如算法题 `judge_result`、文件题 `manual_review`。该方案短期简单，但会导致汇总、权限、考核通过决策逻辑重复。统一评判模型更适合作为考核结果的稳定边界。

评判记录必须包含一个可统计的标准化结果码。所有客观题结果码至少包含：

- `AC`：通过/正确。
- `WA`：错误答案。

算法题在 `AC`、`WA` 基础上额外支持 ACM 类型错误：

- `TLE`：超时。
- `RE`：运行错误。
- `CE`：编译错误。
- `MLE`：内存超限。

单选题和多选题只使用 `AC`、`WA`，并且不进入队列、不存在 `PENDING` 评判结果，因为提交后必须同步给出结果。算法题使用完整 ACM 类型结果码。文件上传题可使用 `PENDING_MANUAL`、`MANUAL_PASSED`、`MANUAL_FAILED`，但不进入“客观题自动通过率”统计。

沙盒、Worker、队列或基础设施异常不应写成考生的 judgement result code。此类异常属于判题任务状态，应保持任务在队列中等待重试，或标记为可重试/需人工排查的 job 状态；在成功完成一次有效判题前，不产生正式评判结果，也不进入通过率统计。

### 自动题和人工题分流

题型评判方式按题型确定：

- `SINGLE_CHOICE`：提交后同步自动评判。
- `MULTIPLE_CHOICE`：提交后同步自动评判，默认完全一致才得分。
- `ALGORITHM`：提交后创建异步判题任务，完成后写入自动评判结果。
- `FILE_UPLOAD`：提交后等待人工评分和评论。

自动题的分数不可被人工覆盖。管理员可查看结果，方向管理员以上负责最终通过/不通过决策。

### 算法题内容结构

算法题使用标准输入输出模型。`starterCode` 的 key 同时作为允许提交语言集合，避免 `allowedLanguages` 与模板字段不一致。

建议内容结构：

```json
{
  "type": "algorithm",
  "content": "题干 Markdown",
  "inputDescription": "输入说明",
  "outputDescription": "输出说明",
  "constraints": "数据范围",
  "examples": [
    { "input": "1 2", "expectedOutput": "3", "explanation": "样例说明" }
  ],
  "runTestCases": [
    { "input": "2 3", "expectedOutput": "5" }
  ],
  "testCases": [
    { "input": "100 200", "expectedOutput": "300", "hidden": true, "weight": 1 }
  ],
  "starterCode": {
    "python": "def solve():\n    pass\n\nif __name__ == \"__main__\":\n    solve()\n"
  },
  "timeLimit": 1000,
  "memoryLimit": 256
}
```

`examples` 用于题面展示，`runTestCases` 用于系统默认运行，`testCases` 用于正式提交判题。三者可以重合，也可以不同。

### 运行和提交分离

算法题提供两个动作：

- 运行：不计分，用于调试。可运行系统默认 testcase 或考生自定义输入。
- 提交：保存正式答案并进入判题队列，生成题目评判结果。

默认 testcase 运行失败时展示输入、期望输出、实际输出。自定义输入没有期望输出，只展示运行状态、stdout、stderr、耗时和内存。提交失败时隐藏测试点也展示失败用例输入、期望输出、实际输出，以保证评判透明。

### 异步队列和沙盒执行

算法题提交接口只保存答案、创建判题任务并投递 RabbitMQ 消息。独立 Judge Worker 消费任务，在沙盒环境中编译/运行代码并写回结果。Spring Boot 主应用不直接执行考生代码。

第一版建议使用 Docker 沙盒，并限制 CPU、内存、运行时间、进程数、网络访问、文件系统访问和输出大小。后续可替换为 gVisor、Firecracker、nsjail 或 isolate，但不影响业务 API。

### 轮询结果

前端提交运行或正式提交后获得 `jobId`，通过查询接口轮询任务状态。轮询状态包括 `PENDING`、`RUNNING`、`RETRYING`、`SUCCEEDED`、`FAILED_REVIEW_REQUIRED`。判题完成后返回用例级结果和题目级评判结果；沙盒或队列基础设施异常只改变 job 状态，不生成考生评判结果。

### 题目通过率统计

通过率统计应基于“每个考生对每道题的最新正式评判结果”，避免多次提交把统计结果放大。当前表结构每题每人唯一答案时可直接按 judgement 聚合；如果未来支持多次提交历史，也应先选最新正式 judgement 再聚合。

客观题统计建议返回：

```json
{
  "questionId": 1,
  "questionType": "ALGORITHM",
  "submittedCount": 30,
  "acceptedCount": 18,
  "passRate": 0.6,
  "resultDistribution": {
    "AC": 18,
    "WA": 7,
    "TLE": 2,
    "RE": 1,
    "CE": 2,
    "MLE": 0
  }
}
```

单选题、多选题的 `resultDistribution` 只需要 `AC` 和 `WA`。算法题必须保留 ACM 错误类型分布，供后续管理端分析题目难度、错误类型和通过率。

第一版可以从评判记录实时聚合；如果后续题量或访问量上升，再引入物化统计表或定时刷新缓存。无论是否物化，源数据都应是标准化 judgement result code。

## Risks / Trade-offs

- 隐藏用例失败详情会泄露测试点 -> 这是明确接受的透明性取舍；后续如需正式考核保护，可再引入 reveal policy。
- Docker 沙盒不是最强隔离 -> 第一版通过资源限制、禁网、临时目录和独立 Worker 降低风险；高安全需求时替换沙盒实现。
- 判题 Worker 故障会导致任务堆积 -> 任务表记录状态和重试次数，支持失败重试和人工排查。
- 轮询会产生额外请求 -> 控制前端轮询间隔和终止条件，任务完成后停止轮询。
- 统一评判模型会触及多个模块 -> 分阶段实现：先数据模型和人工/客观题评判，再算法题运行，最后接入沙盒 Worker。
- 通过率受多次提交策略影响 -> 统计口径固定为每名考生每题最新正式评判结果，未来支持提交历史时仍保持该口径。
- 沙盒或队列异常可能影响实时反馈 -> 任务保持可重试状态并继续排队，无法自动恢复时进入人工排查 job 状态，但不写入考生评判结果、不进入通过率。

## Migration Plan

1. 新增 Flyway migration 创建评判、判题任务、判题用例结果等表；不修改既有 `V1__init_schema.sql`。
2. 扩展 DTO、枚举和 repository，保持旧答案提交接口兼容文件上传题和选择题。
3. 接入单选题、多选题同步自动评判和文件上传题人工评分。
4. 接入算法题内容模型、运行/提交 API、队列和轮询查询 API。
5. 部署 Judge Worker 和沙盒运行环境。
6. 基于 judgement result code 增加题目通过率和结果分布查询能力。
7. 前端逐步开放管理端配置、考生端运行/提交、成员评判查看、题目统计展示、方向管理员通过决策。

## Open Questions

- 文件上传题人工评分是否允许多名成员评分后取平均，还是只保留最新评分。
- 算法题提交是否保留多次提交历史，还是沿用当前每题每人唯一答案并覆盖更新。
- 方向管理员通过决策是否需要记录“自动建议通过/不通过”和“人工最终决定”的差异。
- 题目通过率是否要对考生端开放，还是只在管理端展示；如对考生端开放，是否仅展示自己已提交后的统计。
