## Context

当前系统已有团队成员列表页面（`/members`），展示成员简要信息卡片。UI 设计师已完成成员详情页面的设计，需要实现一个完整的成员信息展示页面。

### 设计文件
- 设计稿位置：`docs/UI/member-profile/index.html` 和 `styles.css`
- 设计风格：深色主题，现代化 UI，包含头像展示、信息卡片、经历展示等模块

### 现有代码结构
- 成员列表页面：`src/app/(public)/(other)/members/page.tsx`
- 成员 API 服务：`src/apis/services/member.service.ts`
- 成员类型定义：`src/apis/schema/type.ts` 中的 `MemberBriefDTO`

### 后端 API
后端已提供成员详情接口：
- `GET /api/v1/members/{id}` - 获取成员详细信息
- 返回 `MemberDetailDTO`，包含基本信息和经历数据

## Goals / Non-Goals

**Goals:**
- 实现成员详情页面，支持通过成员 ID 访问
- 完整还原 UI 设计稿的视觉效果和交互
- 展示成员基本信息、统计数据、经历列表
- 实现 Tab 切换功能（个人信息、项目经历、竞赛经历、实习经历）
- 页面为公开页面，无需登录即可查看
- 支持头像、二维码等图片资源的加载

**Non-Goals:**
- 不包含成员信息编辑功能（属于个人信息页面）
- 不实现经历的增删改查功能
- 不实现考核相关功能
- 不实现 GitHub 链接等未在后端定义的功能

## Decisions

### 1. 页面路由设计

**决定**: 使用动态路由 `/members/[id]/page.tsx`

**理由**: 
- 符合 Next.js App Router 的最佳实践
- 语义清晰，与列表页面 `/members` 保持一致
- 便于未来扩展，如 `/members/[id]/edit` 等

### 2. 组件架构

**决定**: 采用页面组件 + 子组件的架构
- 页面组件：负责数据获取和整体布局
- `MemberProfileSidebar`: 左侧边栏组件（头像、简介、基本信息、统计数据）
- `MemberProfileContent`: 右侧内容组件（Tab 导航、信息面板、经历卡片）
- `ExperienceCard`: 经历卡片通用组件

**理由**:
- 组件职责清晰，便于维护和复用
- 符合现有项目的组件化风格
- 便于未来扩展和修改

### 3. 样式方案

**决定**: 使用 CSS Modules + 设计稿 CSS 变量

**理由**:
- 与现有项目风格一致
- CSS Modules 提供作用域隔离
- 可以直接复用设计稿中的 CSS 变量定义
- 便于主题定制和维护

### 4. 数据获取策略

**决定**: 在页面组件中使用 Server Component 获取数据

**理由**:
- 利用 Next.js 13+ 的服务端渲染能力
- 减少客户端 JavaScript 包体积
- 提升首屏加载性能
- 成员信息为公开数据，无需用户认证

### 5. 图片资源处理

**决定**: 头像和二维码使用后端文件下载接口

**理由**:
- 与后端 API 设计保持一致（使用 `avatarFileId` 而非 `avatarUrl`）
- 统一的文件访问控制
- 符合现有项目的图片加载方式

## Risks / Trade-offs

**性能风险**: 成员详情页面需要加载多个图片资源（头像、二维码、经历附件等）
→ **缓解**: 使用懒加载、图片预加载、CDN 缓存

**数据一致性风险**: 后端 API 返回的数据结构可能与前端类型定义不一致
→ **缓解**: 严格对齐后端 DTO 定义，使用 TypeScript 类型检查

**兼容性风险**: 设计稿中的某些 CSS 效果可能在旧浏览器中不支持
→ **缓解**: 使用现代浏览器支持的 CSS 特性，提供降级方案
