# ai-intent-recognition Specification

## Purpose
运行时意图识别与安全围栏：在用户请求进入 RAG 检索之前分类意图，只放行报名、考核流程、实验室介绍、软件下载四类问题；拦截考核具体内容、代码编写、技术答疑、部署细节、密钥及无关内容；问候与澄清类请求直接回复。分类失败绝不放行检索。

## Requirements

### Requirement: Intent classification determines request handling
The AI service SHALL classify every user chat request into one of three actions (`RETRIEVE`, `REFUSE`, `DIRECT`) based on its intent before invoking the RAG retrieval workflow.

#### Scenario: Allowed intent enters retrieval
- **WHEN** the user asks about registration, assessment process, lab introduction, or software download
- **THEN** the classifier returns `action=RETRIEVE`
- **AND** the request proceeds to the LangGraph RAG workflow

#### Scenario: Blocked intent is refused without retrieval
- **WHEN** the user asks about assessment content details, code writing, technical support, deployment details, security/keys, or irrelevant topics
- **THEN** the classifier returns `action=REFUSE`
- **AND** the request does NOT invoke `tag_generate`, embedding, vector search, or any retrieval tool
- **AND** the response is generated by the refusal message generator

#### Scenario: Greeting intent is answered directly without retrieval
- **WHEN** the user sends a greeting or casual chitchat message
- **THEN** the classifier returns `action=DIRECT`
- **AND** the request does NOT invoke the RAG retrieval workflow
- **AND** the response is generated by the direct-reply generator

### Requirement: Intent taxonomy is fixed and exhaustive
The classifier SHALL use a fixed set of intent labels mapped to the three actions.

#### Scenario: Registration intent
- **WHEN** the user asks how to join or register for the team
- **THEN** the classifier returns `intent=REGISTRATION` and `action=RETRIEVE`

#### Scenario: Assessment process intent
- **WHEN** the user asks about assessment schedule, rounds, or preparation process
- **THEN** the classifier returns `intent=ASSESSMENT_PROCESS` and `action=RETRIEVE`

#### Scenario: Lab introduction intent
- **WHEN** the user asks what the team does, its directions, or general introduction
- **THEN** the classifier returns `intent=LAB_INTRODUCTION` and `action=RETRIEVE`

#### Scenario: Software download intent
- **WHEN** the user asks where to download software or what software a direction uses
- **THEN** the classifier returns `intent=SOFTWARE_DOWNLOAD` and `action=RETRIEVE`

#### Scenario: Assessment content intent is blocked
- **WHEN** the user asks what questions are in the assessment or requests specific assessment problems
- **THEN** the classifier returns `intent=BLOCKED_ASSESSMENT_CONTENT` and `action=REFUSE`

#### Scenario: Coding intent is blocked
- **WHEN** the user asks the assistant to write or debug code
- **THEN** the classifier returns `intent=BLOCKED_CODING` and `action=REFUSE`

#### Scenario: Technical support intent is blocked
- **WHEN** the user asks how to draw a part, read a drawing, tune parameters, or solve an algorithm problem
- **THEN** the classifier returns `intent=BLOCKED_TECH_SUPPORT` and `action=REFUSE`

#### Scenario: Deployment intent is blocked
- **WHEN** the user asks how the website is deployed, server configuration, or infrastructure details
- **THEN** the classifier returns `intent=BLOCKED_DEPLOYMENT` and `action=REFUSE`

#### Scenario: Security intent is blocked
- **WHEN** the user asks for keys, passwords, tokens, or other sensitive configuration
- **THEN** the classifier returns `intent=BLOCKED_SECURITY` and `action=REFUSE`

#### Scenario: Irrelevant intent is blocked
- **WHEN** the user asks something unrelated to the lab team, such as arithmetic or weather
- **THEN** the classifier returns `intent=BLOCKED_IRRELEVANT` and `action=REFUSE`

#### Scenario: Greeting intent is direct
- **WHEN** the user greets the assistant or makes small talk
- **THEN** the classifier returns `intent=GREETING` and `action=DIRECT`

#### Scenario: Clarification intent is direct
- **WHEN** the classifier cannot produce a confident structured result (parse failure, LLM exception, or empty output)
- **THEN** the result is `intent=CLARIFY` with `action=DIRECT`
- **AND** the agent replies with a fixed clarification message listing the supported service scope

### Requirement: Classifier outputs structured JSON
The classifier SHALL produce a structured result containing intent label, confidence score, reasoning, and action.

#### Scenario: Successful structured classification
- **WHEN** the classifier processes a user message
- **THEN** it returns an `IntentResult` with `intent`, `confidence` in [0, 1], `reason`, and `action`
- **AND** the result is produced via LangChain `with_structured_output` with a Pydantic model

#### Scenario: Classification parse failure is handled gracefully
- **WHEN** the LLM fails to produce valid structured output
- **THEN** the classifier catches the parsing exception
- **AND** returns a `CLARIFY` intent result with `action=DIRECT` (never `RETRIEVE`), so the request cannot silently bypass the guard into retrieval

#### Scenario: Classification service exception cannot bypass the guard
- **WHEN** the intent classifier LLM call raises an exception or times out
- **THEN** the agent returns a fixed clarification reply asking the user to describe whether the question is about registration, assessment process, lab introduction, or software download
- **AND** the request does NOT enter the RAG retrieval workflow

#### Scenario: Inconsistent action is corrected
- **WHEN** the model returns an `action` that contradicts its `intent` label (e.g. a `BLOCKED_*` intent with `RETRIEVE`)
- **THEN** the classifier corrects `action` to the canonical mapping derived from `intent`
- **AND** logs a warning about the inconsistency

### Requirement: Streaming intent classification exposes reasoning
The streaming chat path SHALL classify intent via a streaming LLM call that emits the model's brief analysis as SSE `reasoning` events before the final decision.

#### Scenario: Analysis streamed as reasoning events
- **WHEN** a client calls `POST /ai/v1/chat/stream`
- **THEN** the classification analysis text is streamed as `data: {"type": "reasoning", "content": "..."}` events
- **AND** the JSON classification result itself is never leaked into reasoning events

#### Scenario: Decision marker emitted after analysis
- **WHEN** the streaming classification completes
- **THEN** a reasoning event containing `[意图识别] 判定为 <INTENT>` is emitted, indicating whether the request enters retrieval, is refused, or is answered directly

#### Scenario: Refusal and direct replies are streamed
- **WHEN** the classifier returns `REFUSE` or `DIRECT`
- **THEN** the reply is generated via the LLM streaming interface and emitted as incremental `content` events followed by a single `done` event

### Requirement: Intent classification uses a separately configurable model
The classifier SHALL support a dedicated LLM configuration independent from the main RAG LLM.

#### Scenario: Default fallback to main LLM
- **WHEN** no intent-specific LLM is configured
- **THEN** the classifier reuses the same provider and model as the main RAG LLM

#### Scenario: Dedicated intent LLM
- **WHEN** `TBD_RAG_INTENT_LLM_PROVIDER` and/or `TBD_RAG_INTENT_LLM_MODEL` are set
- **THEN** the classifier uses the configured provider and model

### Requirement: Refusal messages are generated by LLM
Blocked requests SHALL produce a polite refusal message generated by an LLM, constrained to not answer the original question.

#### Scenario: Refusal for blocked technical question
- **WHEN** the classifier returns `action=REFUSE` with `intent=BLOCKED_TECH_SUPPORT`
- **THEN** the refusal generator produces a message explaining that specific technical implementation guidance is not provided
- **AND** it redirects the user to consult senior team members after joining
- **AND** it does NOT answer the technical question

#### Scenario: Refusal for security question
- **WHEN** the classifier returns `action=REFUSE` with `intent=BLOCKED_SECURITY`
- **THEN** the refusal generator states that deployment, keys, and security configuration questions cannot be answered
- **AND** it does NOT reveal any credentials or configuration

### Requirement: Direct replies are generated by LLM
`DIRECT` requests SHALL produce a brief, friendly reply generated by an LLM without retrieval.

#### Scenario: Greeting reply
- **WHEN** the classifier returns `action=DIRECT` with `intent=GREETING`
- **THEN** the direct-reply generator returns a short greeting
- **AND** it offers to help with registration, assessment process, lab introduction, or software download questions

### Requirement: Intent classification considers recent conversation context
The classifier SHALL use the most recent user message as the primary signal and include the last few turns of conversation as context when available.

#### Scenario: Context resolves ambiguous follow-up
- **WHEN** the previous turn discussed registration and the current message is "考核难吗"
- **THEN** the classifier uses both the current message and prior context to classify the intent as `ASSESSMENT_PROCESS`

### Requirement: Classification results are observable
The AI service SHALL log every intent classification outcome for monitoring and tuning.

#### Scenario: Logging on classification
- **WHEN** the classifier returns a result
- **THEN** a log entry records the user message, intent, confidence, action, and reasoning
