# CI-CD自动部署

本文档介绍 BlueNet 的 GitHub Actions CI/CD 流水线：**CI 自动、CD 受 trigger 版本号控制、镜像按版本号管理**。

## 架构概览

```mermaid
flowchart TD
    subgraph 触发
        A[Push 到 master/main/develop] --> B[CI 工作流]
        A -.docs 等无关路径.->|不触发| X
        M[手动 workflow_dispatch] --> C[CD Deploy 编排器]
    end

    subgraph CI（每次 push 自动）
        B --> B1[路径过滤只测/构建变更的服务]
        B1 --> B2[构建镜像：打版本号+sha+latest/develop tag]
        B2 --> B3[上传 changed-services.json]
    end

    subgraph CD（CI 成功后触发）
        C --> D[resolve-context 读 trigger/* 版本号 + changed-services]
        D --> E[cd-infra]
        E --> F[cd-api / cd-judge / cd-ai]
        F --> G[backend-gate 轮询后端健康]
        G --> H[cd-frontend 构建并部署]
    end

    B3 --> D
```

## 核心概念

### 1. CI 与 CD 分离

| 环节 | 触发 | 行为 |
|------|------|------|
| **CI**（`.github/workflows/ci.yml`） | 每次 push 到 master/main/develop（除无关路径） | 路径过滤，只对变更的服务测试 + 构建镜像 + 打 tag 推 ghcr |
| **CD**（`.github/workflows/cd-deploy.yml` + `cd-*.yml`） | CI 成功后自动，或手动 `workflow_dispatch` | 按 trigger 版本号部署 |

### 2. trigger 版本号控制 CD

仓库根 `trigger/` 目录，每个服务一个文件，**内容为语义化版本号 `x.y.z`**：

```
trigger/
├─ api          # 内容如 1.4.0
├─ frontend     # 内容如 1.2.0
├─ judge
├─ ai
└─ infra        # 版本号不用于镜像 tag，仅作存在性开关
```

规则：

| 操作 | 效果 |
|------|------|
| **修改版本号并 push**（如 `1.4.0`→`1.5.0`） | **发布**：CI 构建 `1.5.0` 镜像，CD 自动部署 `1.5.0` |
| **只改服务代码，不 bump 版本号** | CI 测试并构建（打当前版本 tag），但**不自动部署** |
| **删除 trigger 文件** | 关闭该服务自动 CD |
| **版本号格式非法**（非 `x.y.z`） | 该服务 CI 构建失败并报错 |

> 注意：`docker/docker-compose.yml` 与 `.github/workflows/**` 的变更视为全量变更，会触发所有服务 CI。

### 3. 镜像 tag 方案

每次 CI 构建产出的 tag：

```
不可变 tag   = trigger/<svc> 版本号（如 1.4.0）     ← 发布/回滚用
浮动 tag     = latest（master/main）/ develop（develop） ← 手动部署用
辅助 tag     = sha-<commit>
```

- **自动 CD** 部署的是本次发布的**版本号 tag**（部署的就是发布的版本）。
- **手动 CD** 部署的是**浮动 `latest`/`develop`**。
- **回滚**：在服务器上指定旧版本号 tag 部署。

## 工作流文件清单

| 文件 | 用途 |
|------|------|
| `.github/workflows/ci.yml` | CI：路径过滤 + 测试 + 构建镜像 |
| `.github/workflows/cd-deploy.yml` | CD 编排器：解析上下文 + 按依赖调度 |
| `.github/workflows/cd-api.yml` | API 部署（拉镜像 → SCP → compose up → 健康检查） |
| `.github/workflows/cd-frontend.yml` | 前端部署（等后端健康 → 构建 → 部署） |
| `.github/workflows/cd-judge.yml` | 判题服务部署 |
| `.github/workflows/cd-ai.yml` | AI 服务部署 |
| `.github/workflows/cd-infra.yml` | 基础设施部署（database+redis / rabbitmq） |

## 发布流程示例

**发布 API 新版本：**

```bash
# 1. 修改 trigger/api 版本号
echo "1.5.0" > trigger/api

# 2. 提交并推送（连同代码改动）
git add trigger/api src/backend
git commit -m "feat: xxx"
git push origin develop
```

push 后：CI 构建 `1.5.0` 镜像 → CD 自动部署到开发环境。

**只改动不发布：** 直接改代码 push，CI 会构建，但不部署。

**暂停某服务自动部署：** `rm trigger/frontend` 并 push。

**手动部署全部最新：**

```bash
# Actions 页面 → CD Deploy → Run workflow → target_service=all
# 或命令行：
gh workflow run cd-deploy.yml --ref develop
```

## 手动部署 / 回滚

### 手动部署

在 Actions 页面运行 `CD Deploy`（`workflow_dispatch`），选择目标服务：

- `target_service=all`：按依赖顺序部署所有存在 trigger 文件的服务
- `target_service=api`：只部署 api 最新镜像（`latest`/`develop`）

也可直接单独运行某个 `cd-*.yml`（如 `cd-api.yml`）单独部署该服务。

### 回滚到指定版本

```bash
# 服务器部署目录执行，指定旧版本号 tag
cd $DEPLOY_PATH
export API_SERVICE_IMAGE=ghcr.io/<owner>/bluenet-api-service:1.4.0
docker compose --profile app up -d api-service
```

## 依赖关系

```
cd-infra（database/redis + rabbitmq）
   └─► cd-api ─► backend-gate（轮询后端健康）
   │                └─► cd-frontend（等后端健康后才构建/部署）
   ├─► cd-judge
   └─► cd-ai
```

前端部署前会**等待 API 健康检查通过**，保证 SSR 构建期预渲染访问的是新版本后端。

## 路径级 CI 过滤

| 服务 | 触发路径 |
|------|---------|
| api | `src/backend/**`、`docker/api-service.Dockerfile`、`trigger/api` |
| frontend | `src/frontend/**`、`docker/frontend.Dockerfile`、`trigger/frontend` |
| judge | `src/judge-service/**`、`docker/judge-service.Dockerfile`、`trigger/judge` |
| ai | `src/ai-service/**`、`docker/ai-service.Dockerfile`、`trigger/ai` |
| infra | `docker/docker-compose.yml`、`docker/.env*`、`trigger/infra` |
| 全部 | `.github/workflows/**`、`docker/docker-compose.yml` |
| 不触发 | `docs/**`、`**/*.md`、`.claude/**`、`scripts/hooks/**` |

## 前置条件与 Secrets

服务器要求、SSH 密钥配置与现有部署一致，参见本文档历史版本及 [04-01-环境配置](./04-01-环境配置.md)。

使用的 Secrets（按服务独立，统一回退规则）：

| 服务 | 专属 Secrets 前缀 | 回退 Secrets 前缀 |
|------|------------------|------------------|
| api-service | `API_DEPLOY_*` | `DEPLOY_*` |
| frontend | `FRONTEND_DEPLOY_*` | `DEPLOY_*` |
| judge | `JUDGE_DEPLOY_*` | `DEPLOY_*` |
| ai | `AI_DEPLOY_*` | `DEPLOY_*` |
| database | `DATABASE_DEPLOY_*` | `DEPLOY_*` |
| rabbitmq | `RABBITMQ_DEPLOY_*` | `DEPLOY_*` |

统一回退规则：所有服务优先使用 `<SERVICE>_DEPLOY_*`，未配置时自动回退到 `DEPLOY_*`。适用字段包括 `HOST`、`PATH`、`USER`、`KEY`、`PORT`。

> 例如：`API_DEPLOY_HOST_DEV` 未配置时，cd-api.yml 使用 `DEPLOY_HOST_DEV`。

GitHub Variables（前端构建与健康检查用）：`BACKEND_HOST`、`BACKEND_PORT`、`SSL_ENABLED`、`AI_SERVICE_HOST`、`AI_SERVICE_PORT`、`AI_SERVICE_SSL_ENABLED`、`AI_SERVICE_PREFIX`。

> 已知限制：健康检查地址使用全局 Variables（当前指向生产域名）。开发/生产健康检查地址如需区分，需按环境拆分 Variables（对应被关闭的 PR #55），待后续处理。

## 常见问题

### 1. 改了代码但没有部署

符合预期——**只改代码不 bump 版本号 = 构建但不自动部署**。如需发布，修改 `trigger/<svc>` 版本号。

### 2. 构建失败提示版本号格式非法

`trigger/<svc>` 内容不是 `x.y.z` 格式（如 `abc`、`1.4`）。检查并改为合法语义化版本号。

### 3. 镜像拉取失败

**错误**：`unauthorized: authentication required` 或 `manifest unknown`。

- 确认该版本号镜像已由 CI 构建（只改代码未发布时，版本号 tag 可能不存在于 ghcr，此时应手动部署 `latest`/`develop` 或 bump 版本）。
- 镜像已公开，或服务器已登录 ghcr。

### 4. 只改前端时 backend-gate 卡住

`backend-gate` 会轮询 API 健康接口最多 5 分钟。若后端确实不可用，前端 CD 会失败——这是预期的依赖保护。

## 实施中的已知坑（2026-08-30 验证记录）

1. **可复用 CD 工作流必须由调用方传 `secrets: inherit`**，否则内部 `${{ secrets.* }}` 全部为空。编排器 `cd-deploy.yml` 的每个 `uses:` 调用都要加 `secrets: inherit`。
2. **SSH 私钥不能经 `GITHUB_OUTPUT` 传递**（多行内容破坏 file command）。私钥直接在 `appleboy/scp-action` / `ssh-action` 的 `with.key` 里引用 secret。
3. **host secret 名是 `DATABASE_HOST_DEV` / `RABBITMQ_HOST_DEV`**（不是 `DATABASE_DEPLOY_HOST_DEV`）。若为同一台服务器部署，`deploy_host` 用 `secrets.DATABASE_HOST_DEV || secrets.DEPLOY_HOST_DEV` 兜底。
4. **`permissions: actions: read` 在工作流级会导致 startup_failure**（GitHub 解析问题）。cd-deploy 用 `contents: read, packages: write`；`download-artifact` 依赖的 `actions: read` 由仓库默认权限提供。
