# 贡献指南

感谢您有兴趣为 BlueNet 做出贡献！

## 贡献类型

- **Bug 修复** — 修复现有功能的问题
- **新功能** — 添加新功能或增强现有功能
- **文档改进** — 改进文档、注释或示例
- **代码重构** — 提高代码质量和可维护性
- **测试用例** — 增加测试覆盖率

## 贡献流程

1. **Fork 仓库** — 点击 GitHub 页面右上角的 Fork 按钮。
2. **克隆仓库** — 将 Fork 的仓库克隆到本地。
3. **创建分支** — 基于 `develop` 创建功能分支：`git checkout -b feat/your-feature`。
4. **进行更改** — 编写代码并确保通过测试。
5. **提交更改** — 遵循提交规范。
6. **推送分支** — 将分支推送到 Fork 仓库。
7. **创建 Pull Request** — 向原仓库提交 Pull Request。

## 提交规范

提交信息必须遵循：

```
<类型>: <简短描述>
```

或带作用域：

```
<类型>(<作用域>): <简短描述>
```

### 提交类型

| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档更新 |
| `style` | 代码格式（不影响功能） |
| `refactor` | 重构 |
| `test` | 测试相关 |
| `chore` | 构建过程或辅助工具变动 |
| `perf` | 性能优化 |
| `ci` | CI/CD 配置变动 |
| `build` | 构建系统变动 |
| `revert` | 回滚提交 |

### 提交规则

1. 冒号后必须有一个空格。
2. 描述至少 5 个字符。
3. 描述不建议以句号结尾。
4. Issue 引用默认使用 `ref #<issue号>`。
5. **禁止**使用 `fixes #<issue号>`、`close #<issue号>` 等会自动关闭 issue 的关键字，除非已明确确认 issue 已完全解决并经过用户同意。

### 示例

```
feat: 添加用户头像上传功能
fix(API): 修复用户认证异常
docs: 更新 README 文档
```

## 分支策略

| 分支类型 | 说明 | 示例 |
|---------|------|------|
| `main` | 生产分支，稳定版本 |
| `develop` | 开发分支，集成最新功能 |
| `feat/*` | 功能分支 | `feat/user-avatar` |
| `fix/*` | Bug 修复分支 | `fix/login-bug` |

保持分支更新：

```bash
git fetch upstream
git rebase upstream/develop
```

## Pull Request 流程

### 提交前检查清单

- [ ] 代码已通过 `spotless:apply` 格式化
- [ ] 所有测试已通过
- [ ] 新功能已添加相应的测试用例
- [ ] 数据库变更已创建 Flyway 迁移脚本
- [ ] 提交信息符合规范

### PR 标题格式

```
<类型>: <简短描述>
```

### 代码审查

- 维护者会审查代码。
- 请及时响应审查意见并修改。
- 审查通过后，由维护者手动合并 PR。

> 注意：禁止使用 `gh pr merge` 等工具自动合并 PR。

## 问题报告

### 报告 Bug

使用 [Bug 报告模板](../.github/ISSUE_TEMPLATE/bug_report.md) 创建 Issue，包含：

- 环境信息（操作系统、JDK 版本等）
- 复现步骤
- 预期行为
- 实际行为
- 相关日志

### 功能请求

使用 [功能请求模板](../.github/ISSUE_TEMPLATE/feature_request.md) 创建 Issue。
