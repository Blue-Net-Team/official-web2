# 测试规范手册

## 1. 概述

本项目采用 **TDD（测试驱动开发）+ 分层测试** 理念。不同技术层有各自独立的职责边界，测试也应分层编写：

- **单元测试**聚焦单一类或函数，验证领域规则、转换逻辑、算法正确性。
- **集成测试**验证跨组件协作、数据库持久化、事务边界与用例编排。
- **端到端测试**从用户视角验证完整业务链路。

分层测试的核心原则是：

1. **明确被测对象所属层级**，再决定使用何种基类与 Mock 策略。
2. **该 mock 的一定要 mock**：上层测试不依赖下层真实实现。
3. **不该 mock 的不要 mock**：在应用层与仓储层集成测试中，数据库、事务、真实 Repository 必须真实运行。
4. **每个测试用例保持独立**，测试数据互不污染，避免隐式依赖执行顺序。

## 2. 后端测试

### 2.1 Controller 测试契约

**目标**：验证 HTTP 契约、权限注解生效、参数校验、统一响应格式。

**基类/注解**：

- 使用 `@SpringBootTest` + `@AutoConfigureMockMvc` 启动最小 Web 上下文。
- 使用 `@Import(TestSecurityConfig.class)` 导入测试安全配置，绕过真实 JWT 解析。
- 测试类继承 `BaseIntegrationTest`。

**Mock 边界**：

- **必须 mock `XxxAppService`**：Controller 只验证 HTTP 层，不依赖应用层真实逻辑。
- **必须 mock `RequestConverter` / `ResponseConverter`**：Controller 测试不验证转换器内部实现。
- 禁止使用真实 Repository、DomainService 或基础设施。

**权限测试**：

- 使用 `@WithSecurityPrincipal` 注入认证用户。
- 受保护接口必须显式声明 `permissions`（与 `@RequiresPermission` 的 `value` 保持一致）。
- 公开接口（`AccessLevel.PUBLIC`）不添加权限。

**清理**：

- 每个测试方法结束后调用 `UserCTX.clear()`，避免安全上下文在测试间泄漏。

**示例**：

```java
@SpringBootTest
@AutoConfigureMockMvc
@Import(TestSecurityConfig.class)
class AssessmentAnswerControllerTest extends BaseIntegrationTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private AssessmentAnswerAppService assessmentAnswerAppService;

    @MockitoBean
    private AssessmentAnswerRequestConverter requestConverter;

    @MockitoBean
    private AssessmentAnswerResponseConverter responseConverter;

    @AfterEach
    void tearDown() {
        UserCTX.clear();
    }

    @Test
    @WithSecurityPrincipal(userId = 100L, permissions = {"assessment:answer:create"})
    void createAnswer_shouldReturn200() throws Exception {
        // stub AppService / Converter，执行 MockMvc 请求并断言
    }
}
```

### 2.2 Application 集成测试契约

**目标**：验证用例编排、事务边界、Repository 持久化、领域服务协作。

**基类**：

- 继承 `BaseIntegrationTest`。
- 使用真实数据库（以项目测试配置为准）。

**依赖策略**：

- **Repository 必须真实**：使用 `@Autowired` 注入真实 Repository。
- **DomainService 分两种情况**：
  - 有 `@Transactional` 注解的 DomainService：使用真实 bean，参与应用层事务。
  - 无 `@Transactional` 注解的 DomainService：使用 `@MockitoBean` mock，stub 其领域规则判断结果。
- **外部基础设施必须 mock**：如消息队列发布器、第三方客户端、缓存、文件存储等。
- **其他 ApplicationService 可 mock**：当测试目标不是该协作者时，可用 `@MockitoBean` 替换。

**判断 DomainService 是否需要 mock 的方法**：

查看实现类或方法是否带有 `@Transactional`：

```bash
# 检查所有 DomainService 的事务注解
grep -R "@Transactional" src/main/java/com/bluenet/web/domain/service/impl/
```

### 2.3 Domain 单元测试契约

**目标**：验证领域规则、实体行为、值对象校验。

**环境**：

- 纯 JUnit 5 + Mockito，不启动 Spring 上下文。
- 使用 `@ExtendWith(MockitoExtension.class)` 或 `MockitoAnnotations.openMocks(this)`。

**Mock 边界**：

- 可 mock `Repository` 接口。
- 禁止 mock 被测实体本身。
- 禁止引入 Spring Bean 或基础设施。

### 2.4 RepositoryImpl 集成测试契约

**目标**：验证自定义 SQL、复杂查询、分页、聚合统计。

**基类**：

- 继承 `BaseIntegrationTest`。
- 使用真实数据库。

**禁止**：

- 不测试简单 CRUD（由 MyBatis-Plus 保证）。
- 不引入 Service 或 Controller。

### 2.5 Converter 单元测试契约

**目标**：验证 DTO ↔ Command/Result/Entity 的转换逻辑，尤其是条件分支、枚举映射、空值处理。

**环境**：

- 纯 JUnit 5，不启动 Spring。
- 被测 Converter 直接 `new` 出来。

### 2.6 ArchUnit 架构守护

**目标**：通过单元测试强制分层依赖规则。

**已有规则**：

- `ConverterLayerArchTest`：API Converter 必须按 `Entity → Result → ResponseDTO` 链路转换。

**推荐扩展规则**：

- Controller 不得直接调用 `*Repository`。
- Application 层不得依赖 infrastructure 具体实现（接口注入除外）。
- Domain 层不得依赖 `api.*` / `infrastructure.*` 包。
- RepositoryImpl 返回类型不得命名为 `*VO`。

### 2.7 角色与权限测试

#### 2.7.1 角色名称定义

系统角色名称统一使用**大写下划线**格式：

| 角色名 | 说明 |
|--------|------|
| SUPER_ADMIN | 超级管理员 |
| DIRECTION_ADMIN | 方向管理员 |
| MEMBER | 团队成员 |
| CANDIDATE | 考生（报名通过后自动分配） |

#### 2.7.2 测试中设置用户角色

由于数据库迁移脚本中插入的角色**没有指定ID**（使用数据库自增），测试时不能直接通过ID设置用户角色，必须先通过角色名查找角色ID：

```java
@SpringBootTest
class ExampleIntegrationTest {

    @Autowired
    private RoleMapper roleMapper;

    private Long memberRoleId;
    private Long candidateRoleId;

    @BeforeEach
    void setUp() {
        // 正确：通过角色名查找角色ID
        Role memberRole = roleMapper.selectByName("MEMBER");
        assertNotNull(memberRole, "MEMBER 角色应存在");
        memberRoleId = memberRole.getId();

        Role candidateRole = roleMapper.selectByName("CANDIDATE");
        assertNotNull(candidateRole, "CANDIDATE 角色应存在");
        candidateRoleId = candidateRole.getId();

        // 然后使用查找到的ID创建用户
        User user = User.create(
            "2024001001",           // studentId
            "test@example.com",     // email
            memberRoleId,           // roleId
            encodedPassword,        // password
            "测试用户",              // username
            null, null, null, null, null, null, null, null, null, null, null, null
        );
    }
}
```

#### 2.7.3 错误示例

```java
// 错误：不要硬编码角色ID，且禁止使用 Builder 模式创建领域实体
User user = User.create(
    "2024001001", "test@example.com", 1L, encodedPassword,
    "测试用户", null, null, null, null, null, null, null, null, null, null, null, null, null
);  // ❌ 错误：ID可能因数据库状态不同而变化
```

#### 2.7.4 使用 @WithSecurityPrincipal 注解

单元测试可使用 `@WithSecurityPrincipal` 注解模拟已认证用户：

```java
@Test
@WithSecurityPrincipal(
    userId = 1L,
    studentId = "2024001001",
    username = "张三",
    roleType = RoleType.MEMBER,
    permissions = "user:info:me"
)
void testUserInfo() {
    // 测试逻辑
}
```

`@WithSecurityPrincipal` 会构造一个 `SecurityPrincipal` 放入 `UserCTX`，与安全上下文实际运行时保持一致。

#### 2.7.5 清理安全上下文

在每个使用 `@WithSecurityPrincipal` 的测试方法或类中，应通过 `@AfterEach` 调用 `UserCTX.clear()`，防止上下文泄漏影响后续用例。

```java
@AfterEach
void tearDown() {
    UserCTX.clear();
}
```

### 2.8 Fixture 使用规范

**目标**：用可复用的 Builder 快速构造测试数据。

**原则**：

- 领域实体通过 `XxxFixture` 创建，不直接 `new` 或硬编码 ID。
- 数据库自增字段（如角色 ID）必须通过查询获取，禁止硬编码。
- 每个测试用独立数据，避免测试间耦合。

### 2.9 断言与比较规范

- `BigDecimal` 比较使用 `compareTo` 或构造相同 scale 的值，避免 `assertEquals` 因 scale 不同失败。
- 集合、分页结果应断言关键字段，避免过度断言无关字段。
- 异常断言使用 `assertThrows`，并验证异常类型和关键消息。

## 3. 前端测试

前端测试目前采用 **Vitest / Jest + React Testing Library + Playwright** 的组合策略，按测试范围分为三层：

### 3.1 单元测试

- **框架**：Vitest（推荐）或 Jest。
- **范围**：纯函数、工具类、Hooks、独立组件。
- **Mock 策略**：
  - API 调用统一 mock `apis/services/*` 或 `apis/client`。
  - 浏览器 API（如 `localStorage`、`fetch`）使用 Vitest/Jest 的 mock 机制替代。
  - 路由、状态管理按需提供 mock Provider。

### 3.2 组件与集成测试

- **框架**：React Testing Library。
- **范围**：页面级组件、表单交互、列表渲染、权限控制渲染。
- **原则**：
  - 优先从用户视角断言（文本、按钮、状态变化），避免断言实现细节。
  - 异步操作使用 `waitFor`、`findBy*` 等工具等待渲染稳定。
  - 与后端交互时，使用 MSW（Mock Service Worker）或统一 stub service 层。

### 3.3 端到端测试

- **框架**：Playwright。
- **范围**：关键用户链路，如报名 → 登录 → 考核答题 → 提交答案 → 查看成绩。
- **原则**：
  - 每个 E2E 用例独立初始化数据，避免测试间状态污染。
  - 优先使用 API 预置测试数据，减少 UI 操作步骤。
  - 断言以页面可见结果为准，必要时结合后端状态校验。

> 具体用例与 fixture 规范应跟随项目实际约定补充。本章为前端测试提供总体方向，后续可在 `src/frontend` 中建立统一的测试工具库与示例用例。
